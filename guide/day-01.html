Day 1 — Monorepo setup

Goal: one repo, three packages (apps/api, apps/web, packages/db), a hosted Postgres (Neon), and a Dockerfile for the API that is ready for deployment.

How we use Docker in this project. You can't run Docker on your PC, and that's fine:
  • Development: run the API with pnpm dev directly on Windows. The database is a hosted Postgres (Neon), not a local container.
  • Production: the API is a Docker image, built by GitHub Actions (Day 2) and pulled by the server. You can run several copies of it to scale. The database is still hosted (Neon/Aiven), never a container.
  • So there is no docker-compose.yml for Postgres anywhere in this guide.

Tasks

All terminal commands in this guide are written for Windows PowerShell. If you see mkdir -p or && in your own notes, that is Linux/bash syntax and will not work here.

1. Root files

terminal
mkdir apps, packages
pnpm init

Create pnpm-workspace.yaml (below) before the next command. -w only works inside a workspace.

package.json (root) — set packageManager to your own pnpm -v, replace scripts
{
  "name": "ev-platform",
  "private": true,
  "packageManager": "pnpm@12.14.0",
  "scripts": {
    "dev": "turbo dev",
    "build": "turbo build",
    "test": "turbo test",
    "db:migrate": "pnpm --filter @ev/db migrate",
    "db:seed": "pnpm --filter @ev/db seed",
    "db:studio": "pnpm --filter @ev/db studio"
  }
}
pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"

# pnpm blocks install scripts by default and asks you to allow or deny each package.
# (pnpm 12 calls this allowBuilds; pnpm 10 called it onlyBuiltDependencies. Don't use both.)
allowBuilds:
  esbuild: true         # compiler used by tsx and tsup; needs its install script
  unrs-resolver: false  # ESLint helper, ships prebuilt, no script needed
  sharp: false          # Next image tool, ships prebuilt
terminal — now install the root tools
pnpm add -Dw turbo typescript
"Ignored build scripts" / ERR_PNPM_IGNORED_BUILDS is not a broken install. A package wants to run an install script, and pnpm waits for your answer. It may add a placeholder line like esbuild: set this to true or false to pnpm-workspace.yaml. Replace it with true (script needed) or false (not needed), then run pnpm install again. You will see this for Prisma on Day 2, where the answer is true.
turbo.json
{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "dev":   { "cache": false, "persistent": true },
    "build": { "dependsOn": ["^build"], "outputs": ["dist/**", ".next/**"] },
    "test":  {}
  }
}
tsconfig.base.json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "resolveJsonModule": true,
    "types": ["node"]
  }
}
"types": ["node"] is required with TypeScript 6 and 7. They no longer load @types/* packages automatically, so without it you get "Cannot find name 'process'" even when @types/node is installed. Every package that uses Node APIs needs @types/node as a dev dependency (@ev/api and @ev/db).

2. Postgres (hosted, no Docker)

  1. Sign up at neon.tech (free tier). Create a project: Postgres version 16, region as close to India as offered (Mumbai if available, otherwise Singapore). Later put your server in the same region, because every query crosses the network.
  2. Neon gives every project a default branch (called production in the current console; older projects say main). Create a second branch called dev and use that for development. Production will use the default branch, so your test data never mixes with real data.
  3. Open Connect on the dev branch and copy two strings:
    • Pooled (turn Connection pooling on, host contains -pooler) → this is DATABASE_URL, used by the running app.
    • Direct (pooling off) → this is DIRECT_URL, used only by prisma migrate.

Why two? Several API containers will each open their own connections. The pooler (PgBouncer) shares a few real connections between all of them, so you won't hit the database's connection limit when you scale. Migrations need a normal direct connection.

what the two strings look like (save them, you'll use them on Day 2)
DATABASE_URL="postgresql://USER:PASSWORD@ep-xxxx-pooler.REGION.aws.neon.tech/neondb?sslmode=require&pgbouncer=true"
DIRECT_URL="postgresql://USER:PASSWORD@ep-xxxx.REGION.aws.neon.tech/neondb?sslmode=require"
These contain your database password. Never commit them. .env is already in .gitignore.
Using Aiven (or any other host) instead? It works the same. Aiven has no separate pooler URL in the basic plan, so put the same URL in both DATABASE_URL and DIRECT_URL and drop &pgbouncer=true. Always keep sslmode=require.

apps/api/package.json — scripts
"type": "module",
"scripts": {
  "dev": "tsx watch src/index.ts",
  "build": "tsup",
  "start": "node dist/index.js",
  "test": "vitest run",
  "sim": "tsx scripts/sim.ts"
}
apps/api/tsconfig.json
{ "extends": "../../tsconfig.base.json", "include": ["src", "scripts"] }
apps/api/tsup.config.ts
import { defineConfig } from "tsup";

// Production build: bundles src/ into dist/index.js (the Docker image runs this file).
export default defineConfig({
  entry: ["src/index.ts"],
  format: ["esm"],
  target: "es2022",
  clean: true,
  // @ev/db is TypeScript source that plain node can't run, so compile it into the bundle.
  noExternal: ["@ev/db"],
});

Temporary entry so pnpm dev works today:

apps/api/src/index.ts
import express from "express";

const PORT = Number(process.env.PORT ?? 4000); // hosts/containers tell us the port via PORT
const app = express();
app.get("/health", (_req, res) => { res.json({ ok: true }); });
const server = app.listen(PORT, () => console.log(`API on port ${PORT}`));

// Docker sends SIGTERM when it stops or replaces a container. Close cleanly instead of being killed.
process.on("SIGTERM", () => server.close(() => process.exit(0)));

4. Dockerfile for the API

You can't build this on your PC, so write it carefully now; GitHub Actions will build it for you on Day 2. Both files live in the repo root, because the build needs the whole monorepo (apps/api and packages/db).

.dockerignore

**/dist
**/.next
**/.env
**/.env.*
.git
.turbo
guide
Dockerfile
FROM node:26-slim AS build
# Prisma's engine needs OpenSSL, which the slim image lacks
RUN apt-get update -y && apt-get install -y openssl && rm -rf /var/lib/apt/lists/*
# Same pnpm as your PC (corepack is not in Node 26). Use the "packageManager" version in your root package.json.
RUN npm install -g pnpm@12.14.0
WORKDIR /app

# Copy only the package files first, so this install layer is cached until dependencies change
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
COPY apps/api/package.json apps/api/
COPY apps/web/package.json apps/web/
COPY packages/db/package.json packages/db/
# (web's package.json is only here so the lockfile matches; its code is never copied or installed)
RUN pnpm install --frozen-lockfile --filter "@ev/api..."

COPY tsconfig.base.json ./
COPY apps/api apps/api
COPY packages/db packages/db
# Generate the Prisma client inside the image so it matches Linux, not your Windows machine
RUN pnpm --filter @ev/db exec prisma generate
RUN pnpm --filter @ev/api build

FROM node:26-slim
RUN apt-get update -y && apt-get install -y openssl && rm -rf /var/lib/apt/lists/*
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app /app
USER node
EXPOSE 4000
HEALTHCHECK --interval=30s --timeout=3s CMD node -e "fetch('http://localhost:'+(process.env.PORT||4000)+'/health').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"
CMD ["node", "apps/api/dist/index.js"]
  • No secrets in the image. .env is excluded. The server passes DATABASE_URL, JWT_SECRET etc. as environment variables at run time. The same image works for staging and production.
  • Why noExternal: ["@ev/db"] in tsup.config.ts? @ev/db is TypeScript source (main: ./src/index.ts), which plain node can't run. This makes tsup compile it into the API bundle. (tsup 9 removed the --noExternal command-line flag, so it must be in the config file.)
  • The image is bigger than it needs to be (it copies the whole build stage). That's fine for the MVP; you can slim it later.
  • This Dockerfile only builds after Day 2, because it needs the Prisma schema. Don't worry if you can't test it today.
Building for scale: rules the code must follow. Several copies of this container can run at once. Keep the API stateless where you can. Anything stored in memory (the OCPP socket Map, bot throttles, background jobs) exists in only one copy. Day 5 and Day 14 say what that means for you; for the MVP, run one container and keep these in mind.
